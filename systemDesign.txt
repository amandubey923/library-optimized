§04  COMPLETE REQUEST LIFECYCLE
════════════════════════════════════════════════════════════════════════════════════════════════════════════════

[IMPORTANT] Traced flow: User opens a book and reads page 42 → flips to page 43

 STEP 01 ── USER ACTION
 ┌───────────────────────────────────────────────────────────────┐
 │ FILE     : app/book/[id]/page.tsx                             │
 │ ACTION   : User navigates to /book/atomic-habits              │
 │ OUTPUT   : Next.js server executes, calls getBookById(id)     │
 │            from data/books.ts, generates OpenGraph meta tags  │
 │ NEXT     : Streams HTML shell + BookDetailClient.tsx          │
 └───────────────────────────────────────────────────────────────┘
          │
          ▼
 STEP 02 ── CLIENT HYDRATION
 ┌───────────────────────────────────────────────────────────────┐
 │ FILE     : app/book/[id]/BookDetailClient.tsx                 │
 │ FUNCTION : useEffect() initializes BookReader with book prop  │
 │ INPUT    : book: Book (from server-rendered props)            │
 │ OUTPUT   : Mounts <BookReader book={book} />                  │
 │ NEXT     : BookReader.tsx initialization                      │
 └───────────────────────────────────────────────────────────────┘
          │
          ▼
 STEP 03 ── PROGRESS HYDRATION (Sub-Millisecond)
 ┌───────────────────────────────────────────────────────────────┐
 │ FILE     : components/reader/BookReader.tsx                   │
 │ FUNCTION : useEffect() → reader-storage.ts.getSavedProgress() │
 │ INPUT    : bookId: "atomic-habits", uid: "usr_abc123"         │
 │ LOGIC    : Checks progressCache Map first (hit = 0ms)         │
 │            Falls back to localStorage.getItem(key)            │
 │            Key: readershub:progress:v1:usr_abc123:atomic-habits│
 │ OUTPUT   : { page: 42, totalPages: 320, progress: 13.1 }      │
 │ NEXT     : setCurrentPage(42), PDF.js render page 42          │
 └───────────────────────────────────────────────────────────────┘
          │
          ▼
 STEP 04 ── PDF ASSET FETCH + SERVICE WORKER
 ┌───────────────────────────────────────────────────────────────┐
 │ FILE     : public/sw.js                                       │
 │ FUNCTION : fetch event listener intercepts /pdfs/*.pdf        │
 │ LOGIC    : sw.js does NOT cache PDFs by default in App Shell  │
 │            If user cached book offline → CacheStorage.match() │
 │            Otherwise → network fetch from Vercel CDN          │
 │ OUTPUT   : PDF binary stream                                  │
 │ NEXT     : PDF.js Web Worker processes binary                 │
 └───────────────────────────────────────────────────────────────┘
          │
          ▼
 STEP 05 ── PDF.JS CANVAS RENDERING (Off Main Thread)
 ┌───────────────────────────────────────────────────────────────┐
 │ FILE     : components/PdfReader.tsx                           │
 │ FUNCTION : renderPage(pageNumber, scale, viewport)            │
 │ INPUT    : pageNumber: 42, scale: 1.15, devicePixelRatio: 2  │
 │ LOGIC    : PDF.js Worker renders vector ops → ImageData       │
 │            Canvas double-buffering eliminates flicker         │
 │            SVG text layer overlaid for selection/highlight    │
 │ OUTPUT   : Painted <canvas> + invisible <div> text layer      │
 │ NEXT     : User can read, annotate, draw                      │
 └───────────────────────────────────────────────────────────────┘
          │
          ▼
 STEP 06 ── USER TURNS PAGE (Right Arrow / Swipe)
 ┌───────────────────────────────────────────────────────────────┐
 │ FILE     : components/reader/BookReader.tsx                   │
 │ FUNCTION : handleNextPage() — keyboard/touch event listener   │
 │ INPUT    : KeyboardEvent: "ArrowRight" or TouchEvent: swipe   │
 │ LOGIC    : setCurrentPage(prev => prev + 1)                   │
 │            Triggers re-render with page 43                    │
 │ NEXT     : Synchronous localStorage write                     │
 └───────────────────────────────────────────────────────────────┘
          │
          ▼
 STEP 07 ── SYNCHRONOUS LOCAL STORAGE COMMIT (<1ms)

[FACT] Reader's HUB uses TWO SEPARATE storage planes:

  PLANE 1 — Browser localStorage (Primary)       PLANE 2 — Cloud Firestore (Secondary)
  ─────────────────────────────────────────       ──────────────────────────────────────
  Speed    : Sub-millisecond (<1ms)               Speed    : 50-200ms (network latency)

  Offline  : Yes, fully functional                Offline  : No (network required)

§20  DESIGN PATTERNS APPLIED
════════════════════════════════════════════════════════════════════════════════════════════════════════════════

PATTERN 1 — SINGLETON
─────────────────────
  Where    : lib/firebase.ts, lib/firebase-admin.ts
  Evidence : getApps().length === 0 ? initializeApp(config) : getApp()
  Why      : Firebase SDK throws if initialized multiple times across Next.js hot reloads
  Interview: "I used lazy Singleton getters for both Firebase Client and Admin SDKs.
              Before each initialization, the getter checks if an existing app instance
              is registered to guarantee one shared connection pool."

PATTERN 2 — FACADE
───────────────────
  Where    : context/LibraryContext.tsx
  Evidence : Component calls toggleFavorite(bookId). Context handles: localStorage write,
             memory cache update, debounced Firestore sync — all hidden from the component.
  Why      : Hides immense complexity of dual-storage, caching, and sync coordination.
  Interview: "LibraryContext acts as a Facade. A BookCard simply calls toggleFavorite().
              Behind that facade, the context coordinates local cache invalidation,
              localStorage commits, and background Firestore synchronization."

PATTERN 3 — STRATEGY (Model Cascade)
──────────────────────────────────────
  Where    : app/api/chat/route.ts, app/api/translate/route.ts
  Evidence : Array of model names iterated in for loop with Promise.race(8s timeout)
  Why      : Preview Gemini models get deprecated or rate-limited unexpectedly.
             The cascade ensures service continuity by automatically switching strategies.
  Interview: "I implemented the Strategy pattern for AI resilience. Each Gemini model
              is a candidate strategy executed with an 8-second timeout. On failure,
              the next model is activated — providing transparent fault tolerance."

PATTERN 4 — DEBOUNCE (Write Coalescing)
─────────────────────────────────────────
  Where    : lib/firestore-sync.ts
  Evidence : progressDebounceTimers, activityDebounceTimers — NodeJS.Timeout maps
  Why      : 300-page reading session → would generate 300 Firestore writes without debounce.
             Debounce coalesces to ~1-3 writes. Reduces DB cost by >90%.
  Interview: "I applied the Debounce pattern to all Firestore write operations.
              Rapid page flips are coalesced into a single write after 3 seconds of
              inactivity, reducing Firestore write costs by over 90%."

PATTERN 5 — REPOSITORY / STORAGE ABSTRACTION
──────────────────────────────────────────────
  Where    : lib/reader-storage.ts
  Evidence : Components never call localStorage directly. All calls go through
             saveProgress(), getAnnotations(), etc.
  Why      : Centralizes serialization, key generation, cache management, and error handling.
  Interview: "I built a Repository abstraction over localStorage. Components interact
              with typed domain methods. The underlying engine handles key namespacing,
              in-memory caching, JSON serialization, and error recovery."

PATTERN 6 — CONTEXT PROVIDER (Dependency Injection)
─────────────────────────────────────────────────────
  Where    : context/AuthContext, LibraryContext, EntitlementContext
  Evidence : Nested providers in app/layout.tsx wrap the entire component tree
  Why      : Eliminates prop-drilling. Navbar and BookReader can both access reading state
             without passing props 8 levels deep.
  Interview: "I used the Context Provider pattern as a form of Dependency Injection.
              Three independent context domains — Auth, Library, and Entitlements —
              each expose memoized state and actions to the entire component tree."

§21  ARCHITECTURAL DECISIONS & TRADEOFFS (ADRs)
════════════════════════════════════════════════════════════════════════════════════════════════════════════════

ADR-1 ── LocalStorage First, Firestore Second
──────────────────────────────────────────────
  DECISION   : Use browser localStorage as the primary data store.
               Firestore is a secondary async backup, not the source of truth.
  [FACT]     : lib/reader-storage.ts handles all reads. firestore-sync.ts writes after debounce.
  BENEFIT    : Sub-millisecond reads. Works without internet. Works without login.
               Zero Firestore read costs for catalog browsing.
  TRADEOFF   : Data is device-local for guests. Device switching requires login.
               5MB localStorage limit could be hit by heavy annotation users.
  ALTERNATIVE: Cloud-first (all reads from Firestore) — rejected: 50-300ms latency on every action.

ADR-2 ── Static JSON Catalog vs. Database-Driven Catalog
──────────────────────────────────────────────────────────
  DECISION   : Bundle all 386+ books in data/books.json at build time.
               Dynamic overrides managed via Firestore catalog_overrides collection.
  [FACT]     : data/books.ts exports BOOKS = booksData. Admin catalog route merges overrides.
  BENEFIT    : Instant client-side search and filtering. Zero DB reads for browsing.
               Full offline catalog availability.
  TRADEOFF   : Adding books requires a code commit + Vercel deployment.
  ALTERNATIVE: Full database catalog (Firestore) — rejected: latency + reads cost per session.

ADR-3 ── Catalog Grounding for Gemini (No RAG)
────────────────────────────────────────────────
  DECISION   : Inject entire catalog summary into Gemini system instruction.
               No vector database, no RAG pipeline.
  [FACT]     : lib/library-assistant.ts → getCompactCatalogSummary() injects catalog context.
  BENEFIT    : Zero hallucinations. No external vector DB infrastructure. Simple to maintain.
  TRADEOFF   : ~2,000 tokens consumed per AI request for catalog context.
  ALTERNATIVE: Pinecone / Weaviate RAG — rejected as unnecessary overhead given catalog fits in context window.

ADR-4 ── Feature-Flag Driven Monetization
───────────────────────────────────────────
  DECISION   : PRO_ENFORCEMENT_ENABLED=false makes all Pro features free during Razorpay KYC.
  [FACT]     : lib/monetization-config.ts defines the flag. EntitlementContext evaluates it.
  BENEFIT    : Builds organic user base before payments activate. No broken checkout experience.
  TRADEOFF   : Zero subscription revenue during promotional period.
  ALTERNATIVE: Block features until payments active — rejected: poor UX and user acquisition loss.

ADR-5 ── PDF.js Client-Side Rendering vs. Server-Side Tile Generation
───────────────────────────────────────────────────────────────────────
  DECISION   : Render PDFs entirely in the browser using PDF.js Web Worker.
  [FACT]     : public/vendor/pdfjs/ is vendored. PdfReader.tsx uses Web Worker explicitly.
  BENEFIT    : Zero server CPU for rendering. True offline reading. No binary transfer overhead.
  TRADEOFF   : Client devices with limited RAM must handle rendering workload.
  ALTERNATIVE: Server-side PNG tile rasterization — rejected: cost + no offline capability.

─── 1-MINUTE VERSION ────────────────────────────────────────────────────────────────────────────────────────
"Reader's HUB is a full-stack PWA built on Next.js 16 App Router with React 19 and TypeScript. The key
architectural decision was to make the platform completely functional without any server round-trip for reading:
all book progress, annotations, highlights, canvas sketches, and streak calculations are persisted immediately
to namespaced browser localStorage through a custom abstraction layer in lib/reader-storage.ts.

When a user authenticates via Google OAuth through Firebase, a background sync engine in lib/firestore-sync.ts
uses debounced timers to push their data to Cloud Firestore, coalescing rapid page flips into single writes
to reduce database costs.

The static book catalog — 386 books — is bundled at build time as a JSON file, making all search and filtering
instantaneous without any database calls. Dynamic admin modifications are handled via a Firestore catalog_overrides
collection that gets merged at runtime.

Two Gemini-powered endpoints provide grounded AI chat — where the catalog is injected into the system prompt to
prevent hallucinations — and real-time bilingual page translation. The platform is deployed on Vercel and is a
fully installable PWA with offline reading support."

─── 3-MINUTE VERSION ────────────────────────────────────────────────────────────────────────────────────────
"Reader's HUB is a digital reading environment designed around one core principle: zero friction. Users can
open a book and start reading immediately — no signup, no ads, no paywalls.

Architecturally, I made a deliberate decision to invert the typical cloud-first model. Instead of fetching
reading data from a server on every interaction, the entire reading experience runs locally in the browser.
lib/reader-storage.ts provides a namespaced localStorage abstraction with in-memory Map caches, so reading
progress, annotations, canvas drawings, and streak data are committed in under a millisecond. For authenticated
users, lib/firestore-sync.ts runs in the background with debounce timers — typically 3 seconds — that coalesce
rapid page-flip events into single Firestore document writes, reducing cloud database costs by over 90%.

The book catalog is another architectural decision I'm proud of. Rather than querying a database on every visit,
I compile all 386+ books into a static JSON bundle that ships with the application. This makes the search,
filtering, and offline catalog browsing instantaneous. Administrative changes like soft-deletions are handled
through a small Firestore catalog_overrides collection that gets merged with the static data at runtime.

The AI features use Google Gemini with a cascade failover strategy. For the chat assistant, I first run
deterministic regex matching to handle common questions at zero API cost. If that fails, the system builds a
system instruction that includes a condensed summary of all 386 books — this is the catalog grounding that
prevents the LLM from hallucinating books outside our library. The translation endpoint similarly caches
translated pages locally to avoid repeated API calls.

On the security side, payment verification uses HMAC SHA256 with Node.js's crypto.timingSafeEqual to prevent
timing attacks. All admin routes require both a valid Firebase ID token and email whitelist validation.

The platform is deployed on Vercel as a PWA with a service worker for offline shell caching and a separate
CacheStorage layer for offline PDF reading."

─── 5-MINUTE DEEP DIVE ──────────────────────────────────────────────────────────────────────────────────────
[Deliver the 3-minute version, then extend into tradeoffs and scaling:]

"Let me talk through the five most interesting architectural decisions and their tradeoffs:

1. Client-First Dual Storage Architecture:
The most important decision was choosing localStorage as the primary data plane rather than Firestore. This
gives us sub-millisecond reads that feel instantaneous even on slow mobile connections, and the reading
experience works completely offline. The tradeoff is that data is device-local for guests — if someone reads
on their phone and then switches to their laptop without logging in, the progress doesn't transfer. We accept
this tradeoff because the zero-friction reading experience is the platform's core value proposition. For logged-in
users, reconcileAndSyncAllUserData() merges cloud records with local records on login, taking the higher page
count and unioning favorites sets.

2. Static JSON Catalog vs. Dynamic Database:
Bundling 386 books as a static JSON file means catalog search and filtering are instantaneous — literally
array.filter() running in under 2 milliseconds. The cost is that adding books requires a code commit and
redeployment. But our ingestion pipeline (scripts/ingest-batch.ts) makes this a single CLI command that
auto-extracts metadata, rasterizes covers, and updates the JSON. The hybrid approach — static JSON plus Firestore
catalog_overrides for admin soft-deletions — gives us the best of both worlds.

3. Gemini Grounding Without RAG:
I avoided building a vector database and RAG pipeline by simply injecting the entire catalog summary into
Gemini's system instruction. At our catalog size (~2,000 tokens for 386 books), this fits comfortably within
the context window. The tradeoff is that each AI request carries this overhead. If the catalog grew to 5,000+
books, we'd need to move to a proper RAG architecture with Pinecone or similar. The deterministic fast-path
also saves significant API costs — common questions like 'show CS books' never reach the LLM at all.

4. Timing-Safe Payment Verification:
The payment flow uses a two-step design where the server creates orders with server-verified pricing — the client
only passes a planId, never a price. Verification uses crypto.timingSafeEqual to compare HMAC SHA256 signatures
in constant time, preventing timing attacks where an attacker could analyze response time deltas to guess
signature bytes. This is a subtle but critical security consideration.

5. PWA Without a Full Framework:
Rather than using next-pwa or similar libraries, I implemented the service worker manually. This gives precise
control over the caching strategy — network-first for navigation, cache-first for static assets, and complete
bypass for API routes. The offline PDF reading is handled through CacheStorage, separate from the app shell cache,
so users can selectively download individual books without caching the entire library."

Q3: How does reading progress persist and sync?
    TESTING   : Dual-storage architecture and debounce pattern knowledge
    ANSWER    : Page turns call saveProgress() in reader-storage.ts. This writes synchronously to an in-memory
                Map cache (<1ms) and then to localStorage. Simultaneously, syncReadingProgressToCloud() in
                firestore-sync.ts clears any existing 3-second debounce timer and sets a new one. After 3s of
                inactivity, the latest progress is flushed to Firestore users/{uid}/reading_progress/{bookId}.
    FILE      : lib/reader-storage.ts, lib/firestore-sync.ts
    FOLLOW-UP : What happens if the browser closes during the 3-second debounce window?

Q4: How does the AI assistant avoid recommending books that don't exist?
    TESTING   : LLM grounding, practical AI engineering
    ANSWER    : The catalog is grounded in the system instruction. getCompactCatalogSummary() condenses all
                386 books by category. This is injected into Gemini's system instruction with strict rules:
                "ONLY recommend books present in this catalog. Return valid JSON." The response bookIds are
                then validated against the static BOOKS array. Additionally, tryDeterministicQuery() intercepts
                common questions with regex patterns before calling Gemini at all.
    FILE      : lib/library-assistant.ts, app/api/chat/route.ts
    FOLLOW-UP : What is the token cost of this grounding approach?

Q5: How is the Razorpay payment signature verified?
    TESTING   : Cryptographic security, payment security knowledge
    ANSWER    : After user pays, the client sends razorpay_order_id, razorpay_payment_id, and
                razorpay_signature to /api/payment/verify. The server computes:
                HMAC = crypto.createHmac("sha256", RAZORPAY_KEY_SECRET)
                            .update(orderId + "|" + paymentId).digest("hex")
                Then uses crypto.timingSafeEqual() to compare byte buffers. This prevents timing attacks
                where an attacker measures nanosecond response differences to guess valid bytes.
    FILE      : lib/razorpay.ts, app/api/payment/verify/route.ts
    FOLLOW-UP : Why can't the client calculate the order amount?

── ADVANCED ─────────────────────────────────────────────────────────────────────────────────────────────────

Q6: What happens when the AI service goes down?
    TESTING   : Fault tolerance, cascading failure design
    ANSWER    : Both /api/chat and /api/translate implement a 5-model cascade. Each model attempt is wrapped
                in Promise.race(8,000ms timeout). If model 1 times out or returns 429/503, the catch block
                moves to model 2. If all 5 fail, the route returns 503 with a user-facing error. On the
                client, Toast.tsx displays a non-blocking notification. The reading experience itself is
                completely unaffected since it runs locally.
    FILE      : app/api/chat/route.ts, app/api/translate/route.ts
    FOLLOW-UP : How would you add proper circuit breaker pattern here?

Q7: How does the app work completely offline?
    TESTING   : PWA architecture, Service Worker, CacheStorage knowledge
    ANSWER    : Two offline layers: 1) The app shell (icons, manifest) is cached by sw.js using Cache-First
                strategy during Service Worker install. 2) Individual books are cached when user clicks
                "Download Offline" — LibraryContext.cacheBookOffline() fetches the full PDF binary and stores
                it in a dedicated CacheStorage bucket ("readers-hub-books-offline-v1"). When offline, sw.js
                intercepts /pdfs/*.pdf requests and serves from cache. PDF.js renders entirely in the browser.
    FILE      : public/sw.js, context/LibraryContext.tsx
    FOLLOW-UP : How do you handle CacheStorage quota limits on mobile devices?
