§01  PROJECT OVERVIEW
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  WHAT IS IT?
  ───────────
  Reader's HUB is a modern, full-stack, Progressive Web App (PWA) digital reading library.
  It provides free access to 386+ curated books — world classics, Hindi literature, philosophy,
  technical/CS books, and self-development titles — directly in the browser as PDF files.
  Zero login is required to read. Authentication (Google Sign-In) is optional and unlocks
  cloud sync, social features, and streak tracking.

  MAIN PURPOSE
  ────────────
  To democratize access to literature and knowledge — specifically targeting Indian readers —
  with a zero-barrier, mobile-first, bilingual (Hindi + English), offline-capable reading
  experience. The tagline: "Stories worth reading. Ideas worth remembering."

  MAJOR FEATURES (verified in code)
  ──────────────────────────────────
  ✦ Full PDF reading with custom in-browser reader (PDF.js + pdfjs-dist vendor)
  ✦ Page-level annotations: highlights, sticky notes, freehand drawing/sketches
  ✦ AI Library Assistant  → Gemini API chat grounded on the catalog
  ✦ AI Page Translation   → Gemini API translates pages to Hindi / Hinglish / English
  ✦ Daily Reading Streaks → "Diwali Diya" flame icon, 15-min/day goal
  ✦ Local reading analytics: heatmaps, genre breakdown, most-read books, session history
  ✦ Offline reading (Service Worker + Cache API)
  ✦ Favorites / My Shelf / Collections / Reflections
  ✦ Social: public profiles, followers/following, activity feed, achievements
  ✦ PWA: installable on Android + iOS home screen
  ✦ Multi-theme system: Original (Amber), 6+ themes, dark backgrounds
  ✦ Smart recommendations engine (100% local, deterministic)
  ✦ Reading certificates on book completion
  ✦ Razorpay payment integration (Pro plan ₹49/month, ₹299/year — currently DISABLED)
  ✦ Admin dashboard: soft-delete books, update metadata, audit logs
  ✦ Contact form (Resend email service)
  ✦ Book ingestion scripts (scan PDFs, extract metadata, write books.json)
  ✦ SEO: sitemap.ts, robots.ts, Open Graph, Twitter Card, structured metadata
  ✦ Reading paths (curated learning paths through books)
  ✦ Knowledge insights (AI-generated insights per book)

  WHO USES IT?
  ────────────
  General public — students, literature lovers, philosophy enthusiasts, CS/technical learners —
  primarily Indian readers (Hindi + English bilingual content, Indian payment gateway Razorpay,
  UPI donation support).

  ║  F. MAJOR FEATURE FLOWS                                                     ║
  ╚══════════════════════════════════════════════════════════════════════════════╝

  ── AI LIBRARY ASSISTANT FLOW ──
  User types query → LibraryAssistant.tsx → POST /api/chat
    → tryDeterministicQuery() [library-assistant.ts] → fast local match?
    → If YES: return immediately (0ms Gemini call)
    → If NO: getCompactCatalogSummary() → Gemini generateContent()
       with system instruction grounding it to catalog
    → Try 5 Gemini model versions with 8s timeout each (graceful fallback)
    → Parse JSON response → findBooksByIds() → return {reply, books, suggestedActions}
    → LibraryAssistant.tsx renders result cards

  ── TRANSLATION FLOW ──
  User clicks "Translate" in BookReader → extract current page text via PDF.js
    → POST /api/translate { pages: [{pageNum, text}], targetLanguage: "hindi" }
    → Gemini generateContent() with system instruction for translation
    → Returns JSON: { "42": "Hindi text for page 42..." }
    → BookReader renders TranslationDrawer with result

  ── PAYMENT FLOW (when enabled) ──
  User clicks "Upgrade to Pro" → ProUpgradeModal selects plan
    → EntitlementContext.initiateCheckout(planId)
    → POST /api/payment/create-order { planId, userId }
       → verifyFirebaseIdToken (optional)
       → getPlanConfig() [monetization-config.ts]
       → createRazorpayOrder() [razorpay.ts]
       → Returns { orderId, amount, keyId, ... }
    → Load Razorpay checkout.js script
    → Open Razorpay modal → user pays
    → POST /api/payment/verify { razorpay_order_id, razorpay_payment_id, razorpay_signature }
       → verifyPaymentSignature() HMAC SHA256 [razorpay.ts]
       → constructPurchasedEntitlement() [entitlements.ts]
       → Return entitlement object
    → syncEntitlementToCloud() [firestore-sync.ts]
    → EntitlementContext updates isPro = true

  ── READING STREAK FLOW ──
  BookReader.tsx mounts ReadingSessionTimer
    → Every 60 seconds during active reading:
       → addActiveReadingTime(bookId, seconds) [reader-storage.ts]
       → Updates localStorage: "readershub:reading-activity:v1:{uid}"
       → Key: "YYYY-MM-DD" → { seconds, qualified }
    → When seconds >= 900 (15 minutes): qualified = true
    → DiwaliDiya flame in Navbar animates/lights up
    → calculateStreak() computes currentStreak, longestStreak
    → On user login: synced to Firestore users/{uid}/data/activity

  TWO-LAYER DATABASE STRATEGY
  ────────────────────────────
  This project uses a sophisticated dual-storage architecture:

  LAYER 1: Browser LocalStorage (Primary)
  ────────────────────────────────────────
  • Works for ALL users including guests (no login required)
  • All reading progress, annotations, streak data stored locally first
  • Namespaced with versioned keys per user
  • In-memory Map caches for O(1) repeat reads
  • Survives page refreshes, works offline
  • Schema: All keys follow pattern "readershub:{type}:v1:{uid}:{optional_bookId}"

  LAYER 2: Cloud Firestore (Sync/Backup for logged-in users)
  ────────────────────────────────────────────────────────────
  • Data pushed from LocalStorage → Firestore asynchronously (debounced)
  • Data pulled from Firestore → LocalStorage on login (reconciliation)
  • Conflict resolution: merge strategy (take most complete data)
  • Enables cross-device sync and profile visibility

  ───────────────────────────────
  1. Client (LibraryAssistant.tsx) → fetch('/api/chat', { body: { message } })
  2. route.ts extracts userMessage, validates length (max 800 chars)
  3. tryDeterministicQuery(userMessage) → checks regex patterns for common queries
     → "what books are available?" → returns catalog summary immediately
     → No match → falls through to Gemini
  4. getCompactCatalogSummary() → builds book list grouped by category (~386 entries)
  5. new GoogleGenAI({ apiKey }) → tries 5 model versions with 8s timeout each
  6. ai.models.generateContent({ model, contents, config: { systemInstruction, temperature: 0.2 } })
  7. Parse JSON response → findBooksByIds(parsed.bookIds) → returns full Book objects
  8. Return NextResponse.json({ reply, books, suggestedActions })

§12  SECURITY ARCHITECTURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  AUTHENTICATION
  ───────────────
  FACT: Google OAuth via Firebase. signInWithPopup() with browserLocalPersistence.
  No passwords stored anywhere. Firebase handles all OAuth token management.
  ID tokens are short-lived JWTs. Server verifies via Firebase Admin SDK.

  AUTHORIZATION
  ───────────────
  FACT: Two levels:
  1. Authenticated user: Bearer token in Authorization header, verified server-side
  2. Admin user: email whitelist check against ADMIN_EMAIL environment variable

  PASSWORD HANDLING
  ──────────────────
  FACT: No passwords exist in this system. Google OAuth only.

  PAYMENT SECURITY
  ─────────────────
  FACT (lib/razorpay.ts): Razorpay payment verification uses HMAC SHA256.
  crypto.createHmac("sha256", keySecret).update(`${orderId}|${paymentId}`).digest("hex")
  Uses crypto.timingSafeEqual() to prevent timing attacks on signature comparison.
  RAZORPAY_KEY_SECRET never sent to client. Server always defines plan amounts
  (client cannot pass amount — server reads from monetization-config.ts).

  CORS
  ─────
  FACT (next.config.ts): Cross-Origin-Opener-Policy: "same-origin-allow-popups"
  header added to all routes. This is required specifically for Google Sign-In popup.
  Standard Next.js handles other CORS defaults (same-origin).

  INPUT VALIDATION
  ─────────────────
  FACT: Manual validation in every API route:
  • Email: regex test
  • Username: lowercase, alphanumeric, max 20 chars, min 3 chars
  • Message length: min 10 chars
  • Message body: max 800 chars for AI queries
  • planId: validated against MONETIZATION_PLANS enum (getPlanConfig)
  • Token presence: checks "Bearer " prefix before processing

  SECRETS MANAGEMENT
  ───────────────────
  FACT: All secrets in .env (not committed to git):
  • FIREBASE_SERVICE_ACCOUNT_KEY or FIREBASE_CLIENT_EMAIL + FIREBASE_PRIVATE_KEY
  • GEMINI_API_KEY
  • RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET, RAZORPAY_WEBHOOK_SECRET
  • RESEND_API_KEY
  • NEXT_PUBLIC_* vars are safe to expose (Firebase client config is public)

  FIREBASE CLIENT CONFIG EXPOSURE
  ─────────────────────────────────
  FACT (lib/firebase.ts): Firebase client API key is exposed in code (line 6).
  This is intentional and safe — Firebase client config is designed to be public.
  Security is enforced via Firebase Security Rules on the Firestore database,
  not by hiding the API key.

  XSS PROTECTIONS
  ─────────────────
  FACT: React's JSX escapes all values by default. The only dangerouslySetInnerHTML
  usage is in app/layout.tsx for the theme/PWA initialization script (safe inline).
  No user-generated HTML is rendered without escaping.

  SQL/NOSQL INJECTION
  ────────────────────
  FACT: No SQL database. Firestore SDK uses parameterized queries (no string
  interpolation in query construction). All Firestore document references use
  validated IDs/UIDs. Username is sanitized before use as Firestore document key.

  RATE LIMITING
  ───────────────
  FACT: No explicit rate limiting middleware found. Daily quota tracking
  for AI assistant (5 queries/day) and translation (10 spreads/day) is
  client-side only (localStorage-based) — not enforced server-side.
  INFERENCE: Vercel provides platform-level DDoS protection. No custom rate limiter.

  ADMIN PANEL SECURITY
  ─────────────────────
  FACT (app/api/admin/catalog/route.ts):
  1. Checks for Authorization Bearer header (401 if missing)
  2. verifyFirebaseIdToken(idToken) → validates with Firebase Admin
  3. isAdminUser(verified.email) → email whitelist check (403 if not admin)
  All three checks must pass before any admin action is executed.

§13  ERROR HANDLING & OBSERVABILITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  ERROR PROPAGATION STRATEGY
  ───────────────────────────
  Server (API routes): try/catch → return JSON error response with HTTP status code
  Client (components): try/catch → show Toast notification or inline error message
  Firebase SDK: try/catch with specific error code handling (auth/popup-closed-by-user, etc.)
  Storage: try/catch in every localStorage function → fail silently, return empty/default

  AI ERROR HANDLING (Multi-Model Fallback Pattern)
  ─────────────────────────────────────────────────
  FACT (app/api/chat/route.ts and app/api/translate/route.ts):
  • 5 Gemini models tried in sequence
  • Each has 8000ms timeout via Promise.race([generatePromise, timeoutPromise])
  • If one model fails/times out → console.warn → try next model
  • If all fail → return friendly fallback message to user
  • Never exposes technical error details to end user

  FIREBASE ERROR HANDLING
  ──────────────────────────
  FACT (context/AuthContext.tsx):
  Specific error codes handled with user-friendly messages:
  • auth/popup-closed-by-user → silent (user intentionally closed)
  • auth/popup-blocked → browser popup block message
  • auth/unauthorized-domain → domain whitelist instruction
  • auth/operation-not-allowed → Firebase console configuration message
  • auth/network-request-failed → network error message

  GLOBAL ERROR HANDLER
  ─────────────────────
  INFERENCE: No global Error Boundary component found in the codebase.
  Next.js provides its own error boundary for route-level crashes.
  app/not-found.tsx handles 404 cases.

  LOGGING FORMAT
  ───────────────
  All log statements use bracketed module tags:
  [Firebase], [Firebase Admin], [Auth], [Chat API], [Translate API],
  [Payment API], [Admin API], [Profile API], [ReaderStorage], [CONTACT API]

  MONITORING
  ───────────
  FACT: No external monitoring service (Sentry, DataDog, etc.) found in the codebase.
  INFERENCE: Vercel provides basic function logs and deployment monitoring natively.

§14  PERFORMANCE & SCALABILITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  CACHING STRATEGIES (verified)
  ──────────────────────────────
  1. Image CDN cache: minimumCacheTTL: 2,592,000 (30 days) in next.config.ts
  2. AVIF + WebP image formats for optimal compression
  3. In-memory Maps in reader-storage.ts for localStorage data (avoids repeated JSON.parse)
  4. Deterministic query cache in AI assistant (avoids Gemini API for common queries)
  5. Service Worker: caches PDF files and static assets for offline access
  6. Translation cache: getCachedTranslation() in lib/translator.ts avoids re-translating

  DATABASE OPTIMIZATION
  ──────────────────────
  1. localStorage first → Firestore only for sync (not every operation hits the network)
  2. Debounced Firestore writes (2-5 second delay) prevents write storms during active reading
  3. writeBatch() for atomic multi-document operations
  4. Collection count queries (.count().get()) instead of fetching all documents for followers
  5. Indexes: INFERENCE — Firestore auto-indexes single fields; compound indexes needed for
     complex queries (where + orderBy) likely configured via Firebase console

  ASYNC PROCESSING
  ─────────────────
  1. Dynamic imports: syncUserProfile() is dynamically imported in AuthContext
     → import("@/lib/firestore-sync").then(...)  → reduces initial bundle size
  2. Gemini API calls are async with timeouts — non-blocking response architecture
  3. Background Firestore writes don't block the reading experience

  PAGINATION
  ───────────
  FACT: Library page (app/library/page.tsx) likely implements client-side pagination/virtualization
  over the static BOOKS array (386 items). Server-side pagination for admin APIs (limitCount param).

  BUNDLE OPTIMIZATION (next.config.ts)
  ──────────────────────────────────────
  • optimizePackageImports: ["lucide-react", "@google/genai", "date-fns"]
    → Tree-shakes these packages, only imports used symbols
  • serverExternalPackages: ["firebase-admin"]
    → Prevents firebase-admin from being bundled in client code
  • cpus: 2 → parallel build workers

  POTENTIAL BOTTLENECKS (INFERENCE)
  ───────────────────────────────────
  1. PDF.js rendering is CPU-intensive; large PDFs may slow on low-end mobile
  2. reader-storage.ts stores all annotations in localStorage per book;
     extremely large annotation sets could approach localStorage quota (~5MB)
  3. AI endpoint has no server-side rate limiting — abuse could incur Gemini API costs
  4. All 386 book objects loaded on the client side (books.json ~several hundred KB)
  5. Firestore real-time listener in EntitlementContext (onSnapshot) fires on every auth change

  SCALABILITY CONSIDERATIONS
  ───────────────────────────
  1. HORIZONTAL: Vercel serverless functions auto-scale. No sticky sessions.
  2. DATABASE: Firestore scales to millions of documents. localStorage is per-device.
  3. CDN: Static PDFs served via Vercel CDN globally — scales with zero server changes.
  4. AI COSTS: Gemini API is rate-limited per key. High traffic could exhaust quotas.
  5. CURRENT ARCHITECTURE supports: Low-Medium traffic easily. For viral scale,
     Gemini API rate limits and Firestore write costs would be primary concerns.

§18  DESIGN PATTERNS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  1. CONTEXT PROVIDER PATTERN (React)
  ────────────────────────────────────
  WHERE: context/AuthContext.tsx, context/LibraryContext.tsx, context/EntitlementContext.tsx
  WHAT: Global state shared across component tree without prop drilling
  HOW: createContext() + useContext() + Provider component wrapping the app
  WHY: Reading state (favorites, streaks) needs to be accessible from Navbar,
       BookReader, MyShelf, Profile simultaneously.
  INTERVIEW: "I used React Context for three global state domains: authentication
  state, library/reading state, and monetization entitlements. Each concern is
  isolated in its own context to avoid unnecessary re-renders."

  2. SINGLETON PATTERN
  ─────────────────────
  WHERE: lib/firebase.ts (getFirebaseApp, getFirebaseAuth, getFirebaseDb)
         lib/firebase-admin.ts (getFirebaseAdminApp)
  WHAT: Single shared instances of Firebase SDK objects
  HOW: Module-level `let app = null` + lazy initialization with null check
  WHY: Firebase SDK must only be initialized once per app lifecycle.
       Multiple initializations cause errors.
  INTERVIEW: "I implemented lazy singletons for Firebase initialization because the
  SDK can only be initialized once. Each getter function checks if the instance
  already exists before creating a new one."

  3. STRATEGY PATTERN (AI Model Fallback)
  ────────────────────────────────────────
  WHERE: app/api/chat/route.ts, app/api/translate/route.ts
  WHAT: Array of model names tried in sequence; each is a strategy
  HOW: for...of loop over modelsToTry array; break on first success
  WHY: Gemini model availability varies; fallback ensures service resilience
  INTERVIEW: "I implemented a model fallback strategy in the AI endpoints. If the
  primary model times out in 8 seconds, the system automatically tries the next
  model in the list, ensuring the user always gets a response."

  4. REPOSITORY PATTERN (Storage Layer)
  ──────────────────────────────────────
  WHERE: lib/reader-storage.ts (localStorage) + lib/firestore-sync.ts (Firestore)
  WHAT: Abstracts data persistence behind function interfaces
  HOW: Components never touch localStorage directly; they call storage functions
  WHY: Storage implementation can change without affecting component code
  INTERVIEW: "I abstracted all data persistence into reader-storage.ts. Components
  call functions like saveProgress(), getBookmarks() — they don't know or care
  whether data goes to localStorage, Firestore, or both."

  5. OBSERVER PATTERN (Real-time updates)
  ────────────────────────────────────────
  WHERE: context/AuthContext.tsx (onAuthStateChanged), context/EntitlementContext.tsx (onSnapshot)
  WHAT: Subscribe to Firebase state changes, react to updates
  HOW: Firebase SDK's event listeners + React state setters in callbacks
  WHY: Auth state and Pro status can change externally (other tabs, admin actions)
  INTERVIEW: "Firebase's onAuthStateChanged and Firestore's onSnapshot are both
  implementations of the Observer pattern. I use them to keep the UI in sync
  with authentication and Pro subscription state in real-time."

  6. COMMAND PATTERN (Admin Actions)
  ───────────────────────────────────
  WHERE: app/api/admin/catalog/route.ts
  WHAT: Each admin action is encapsulated as a named command string
  HOW: switch(action) → { "delete_book", "restore_book", "update_book_metadata", ... }
  WHY: Clean, extensible admin operation dispatch; easy to add new admin operations
  INTERVIEW: "The admin catalog API uses a command pattern where each operation
  (delete, restore, update) is a named action in the request body, dispatched
  through a switch statement. This makes adding new admin operations easy."

  7. FACADE PATTERN (LibraryContext)
  ───────────────────────────────────
  WHERE: context/LibraryContext.tsx
  WHAT: Single interface hiding complex interactions between reader-storage, firestore-sync, BOOKS
  HOW: Context exposes clean actions (toggleFavorite, saveProgress) that internally
       coordinate localStorage writes, Firestore syncs, and state updates
  WHY: Components don't need to know about the dual-storage complexity
  INTERVIEW: "LibraryContext is a facade over the entire data layer. A component
  calling toggleFavorite() doesn't need to know it updates localStorage, fires a
  debounced Firestore sync, and updates multiple pieces of derived state."

  8. DEBOUNCE PATTERN (Write Optimization)
  ─────────────────────────────────────────
  WHERE: lib/firestore-sync.ts (progressDebounceTimers, activityDebounceTimers, etc.)
  WHAT: Delays expensive Firestore writes until reading activity stabilizes
  HOW: clearTimeout(timer); timer = setTimeout(writeToFirestore, delay)
  WHY: Prevents hundreds of Firestore writes per reading session; saves costs and
       improves performance
  INTERVIEW: "I debounce all Firestore writes. When a user is turning pages,
  we don't want to write to the database on every page turn. Instead we wait
  2-5 seconds after the last change before pushing to Firestore."

§19  ARCHITECTURAL DECISIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  DECISION 1: LocalStorage First, Firestore Second
  ─────────────────────────────────────────────────
  WHAT: All reading data (progress, annotations, streaks) is stored locally first.
        Firestore is only used for sync/backup for authenticated users.
  EVIDENCE: lib/reader-storage.ts (primary), lib/firestore-sync.ts (secondary)
  BENEFITS:
  • Works without login (zero barrier to reading)
  • Offline reading support
  • Instant read/write (no network latency)
  • No backend cost for unauthenticated usage
  TRADEOFFS:
  • Data lost if user clears browser storage
  • No cross-device sync without login
  • Complex reconciliation logic needed on login
  ALTERNATIVE: Could store everything in Firestore and require login.

  DECISION 2: Static Catalog (books.json) vs. Database-driven
  ─────────────────────────────────────────────────────────────
  WHAT: 386+ books stored in a JSON file (data/books.json) bundled with the app.
        NOT stored in Firestore.
  EVIDENCE: data/books.json, data/books.ts → BOOKS array imported by components
  BENEFITS:
  • Zero database reads for catalog browsing
  • Works offline (bundled in app)
  • Instant filtering and search (in-memory)
  • No Firestore cost per page view
  TRADEOFFS:
  • Adding books requires code deployment (not just database write)
  • Bundle size grows with more books
  • Cannot easily personalize catalog per user at build time
  ALTERNATIVE: Could store in Firestore with caching layer.

  DECISION 3: Gemini Grounding + Deterministic Fallback
  ───────────────────────────────────────────────────────
  WHAT: AI assistant first tries deterministic regex patterns, only calls Gemini
        if no pattern matches. System instruction grounds Gemini strictly to the catalog.
  EVIDENCE: lib/library-assistant.ts (tryDeterministicQuery), app/api/chat/route.ts
  BENEFITS:
  • Fast responses for common queries (zero AI latency)
  • Prevents hallucination (Gemini can't invent books)
  • Reduces Gemini API cost
  TRADEOFFS:
  • Cannot give general literary knowledge (intentionally restricted)
  • Deterministic patterns need maintenance as new query types emerge
  ALTERNATIVE: Pure LLM with no grounding (more flexible but less accurate/safe).

  DECISION 4: Single Admin by Email Whitelist
  ─────────────────────────────────────────────
  WHAT: Admin access controlled by a single hardcoded email address.
  EVIDENCE: lib/admin.ts → ADMIN_EMAIL constant
  BENEFITS: Simple, secure, no complex role management needed for single-admin project
  TRADEOFFS: Not scalable to multiple admins; requires code change to add admin
  ALTERNATIVE: Firestore-based role system.

  DECISION 5: Razorpay Disabled by Feature Flag
  ───────────────────────────────────────────────
  WHAT: Payment enforcement is disabled via PRO_ENFORCEMENT_ENABLED = false.
        All features are free while Razorpay KYC is pending.
  EVIDENCE: lib/monetization-config.ts
  BENEFITS: Can build and test payment UI without blocking readers
  TRADEOFFS: No revenue currently from Pro plans
  INFERENCE: This is a business/legal decision, not a technical limitation.

  Q6: Walk me through the authentication flow in detail.
  ────────────────────────────────────────────────────────
  Testing: Auth implementation knowledge
  Answer: "When the user clicks Sign In, AuthModal calls signInWithGoogle() from
  AuthContext. This sets browserLocalPersistence then calls Firebase signInWithPopup
  with a GoogleAuthProvider that has 'select_account' prompt. On success, Firebase
  returns the User object. AuthContext's onAuthStateChanged listener sets the user
  state. Simultaneously, syncUserProfile() is dynamically imported and called to
  create or update the user's Firestore document at /users/{uid} and /public_profiles/{uid}.
  LibraryContext then detects the user change and calls reconcileAndSyncAllUserData()
  to merge local guest data with any existing cloud data."
  Files: context/AuthContext.tsx, lib/firestore-sync.ts
  Follow-ups: Why browserLocalPersistence? What happens if the user closes the tab?

  Q7: How does reading progress get saved and synced?
  ─────────────────────────────────────────────────────
  Testing: Data flow understanding
  Answer: "BookReader.tsx calls saveProgress(bookId, page, totalPages) from reader-storage.ts
  on every page change. This writes immediately to localStorage with the key pattern
  'readershub:progress:v1:{uid}:{bookId}'. Simultaneously, it calls syncReadingProgressToCloud()
  from firestore-sync.ts. That function uses a debounce timer — it waits 2-5 seconds after
  the last call before writing to Firestore at users/{uid}/reading_progress/{bookId}.
  If the user is offline, only localStorage is written. On next login on a different device,
  reconcileAndSyncAllUserData() merges Firestore data back into localStorage."
  Files: lib/reader-storage.ts, lib/firestore-sync.ts, components/reader/BookReader.tsx

  Q8: How does the payment system work?
  ──────────────────────────────────────
  Testing: Payment integration knowledge
  Answer: "The flow has three steps. First, the client calls POST /api/payment/create-order
  with the planId. The server validates the plan from monetization-config.ts (so the amount
  comes from the server, not the client), calls Razorpay's API to create an order, and
  returns the orderId and key. Second, the client loads Razorpay's checkout JS and opens
  the payment modal. Third, after payment, the client calls POST /api/payment/verify with
  the orderId, paymentId, and signature. The server verifies the HMAC SHA256 signature
  using timingSafeEqual to prevent timing attacks, then constructs the entitlement object
  which is returned and synced to Firestore. Note: payments are currently disabled via
  the PRO_ENFORCEMENT_ENABLED = false feature flag pending Razorpay KYC approval."
  Files: app/api/payment/*, lib/razorpay.ts, lib/entitlements.ts, lib/monetization-config.ts

  Q9: How do reading streaks work technically?
  ─────────────────────────────────────────────
  Testing: Feature implementation depth
  Answer: "ReadingSessionTimer.tsx tracks active reading time. Every 60 seconds while
  the user is actively reading (tab focused, mouse/touch moving), it calls addActiveReadingTime()
  in reader-storage.ts. This accumulates seconds in localStorage under the current date key
  (YYYY-MM-DD). When a day's total reaches 900 seconds (15 minutes), it marks 'qualified: true'
  for that date. calculateStreak() then counts consecutive qualified days walking backwards
  from today or yesterday. The DiwaliDiya flame icon in the Navbar reflects the current streak.
  Data is debounced-synced to Firestore under users/{uid}/data/activity."
  Files: lib/reader-storage.ts (calculateStreak, addActiveReadingTime), components/reader/BookReader.tsx

  Q10: How does the recommendation engine work?
  ──────────────────────────────────────────────
  Testing: Algorithm understanding
  Answer: "It's 100% local and deterministic — no API calls. In lib/recommendations.ts,
  calculateBookSimilarity() scores each candidate book against a target book with a weighted
  scoring system: +10 for same author, +5 for same category, +4 for both being technical books,
  +3 for same resource type, +2 per shared tag, +1 for same language. The system builds
  recommendation sections based on the user's reading history: 'Because you read X', 'More by
  this author', 'Popular in this category'. All computation happens in the browser instantly."
  Files: lib/recommendations.ts

  Q11: How is the dual-storage architecture (localStorage + Firestore) designed to prevent
       data loss or conflicts when a user logs in from a new device?
  ────────────────────────────────────────────────────────────────────────────────────────
  Testing: Distributed state management
  Answer: "The reconcileAndSyncAllUserData() function in firestore-sync.ts implements
  a best-of-both-worlds merge. When a user logs in, it downloads their cloud data from
  Firestore, then compares it with local data field by field. For reading progress, it takes
  the higher page number. For favorites, it takes the union of both sets. For streaks, it
  takes the best streak data. For annotations, it merges arrays. After reconciliation, it
  pushes the merged result back to both localStorage (as new source of truth) and Firestore.
  Guest data (null UID key) is migrated to the user's UID namespace during this process."
  Files: lib/firestore-sync.ts (reconcileAndSyncAllUserData)
  Follow-ups: What if the user reads on two devices simultaneously?

  Q12: The Gemini AI endpoint uses multiple model fallbacks with timeouts.
       Why is this important and what are the tradeoffs?
  ────────────────────────────────────────────────────────────────────────
  Testing: Resilience engineering
  Answer: "Gemini model availability isn't guaranteed — new models can be in preview
  and sometimes unavailable. The timeout (8 seconds) prevents the serverless function
  from hanging indefinitely, which would cause Vercel to return a 504. By trying 5
  models in sequence with Promise.race([generatePromise, timeoutPromise]), we ensure
  the user always gets a response within ~40 seconds worst case. The tradeoff is
  latency — if the first model times out, we've wasted 8 seconds. The ordering places
  lighter/faster models first to minimize average latency. A better approach for
  production at scale would be a circuit breaker pattern that remembers which models
  are currently failing and skips them."
  Files: app/api/chat/route.ts

  Q13: How would you scale this application to handle 10x more users?
  ──────────────────────────────────────────────────────────────────────
  Testing: Scalability thinking
  Answer: "Current bottlenecks to address:
  1. GEMINI API: Rate limits. Solution: Redis-based request queue, or use Gemini's
     built-in retry/quota handling. Could use multiple API keys with round-robin.
  2. FIRESTORE: Write costs at scale. The debouncing already helps. Could add a
     write-behind cache layer (Redis Pub/Sub) to batch Firestore writes.
  3. PDF DELIVERY: PDFs are currently static on Vercel CDN. At high scale, move
     to a CDN like Cloudflare R2 or AWS CloudFront for better geo-distribution.
  4. ANALYTICS: The client-side-only analytics scales infinitely (no server cost).
  5. BOOKS.JSON: At 386+ books it's manageable. At 10,000 books, would need
     server-side search (Elasticsearch/Algolia) instead of in-memory filtering.
  6. SERVICE WORKER: Already handles offline caching — this scales well.
  Architecture-wise, the app is already well-positioned: serverless functions
  auto-scale on Vercel, static assets on CDN, most computation client-side."

  Q14: The admin system uses email whitelist for authorization.
       What are the security risks and how would you improve it?
  ────────────────────────────────────────────────────────────────
  Testing: Security architecture
  Answer: "Current risks:
  1. If the admin email is compromised via Google account phishing, full admin access

  2. The admin email is partially hardcoded ('kumaraman19137@gmail.com' as fallback

  3. No MFA requirement for the admin account.
  Improvements:
  1. Store admin roles in Firestore with a custom claims system (Firebase Custom Claims)
     set via Admin SDK → more granular roles (super_admin, moderator, content_manager)
  2. Require re-authentication (Firebase reauthenticateWithPopup) before admin actions
  3. Add IP allowlisting for admin routes via Vercel Edge Middleware
  4. Enable Firebase Custom Claims so the admin role is embedded in the JWT itself,
     reducing one Firestore lookup per admin request
  5. Add rate limiting on admin endpoints"

  Q15: The reading data is stored client-side. What happens when a user
       reaches localStorage quota limits? How would you redesign this for reliability?
  ─────────────────────────────────────────────────────────────────────────────────────
  Testing: Edge case handling + system redesign
  Answer: "localStorage is typically 5MB per origin. With 386+ books potentially having
  annotations, drawings (stored as coordinate arrays), and reading memories, a heavy
  reader could hit this limit. Current code: every storage call is wrapped in try/catch,
  so quota exceeded errors are caught silently.
  
  For reliability redesign:
  1. Use IndexedDB (via idb library) instead of localStorage for larger capacity (50MB+),
     structured queries, and proper error handling
  2. Implement a storage pressure monitor that detects approaching quota and prompts
     user to export/purge old data
  3. Prioritize storage: progress > bookmarks > highlights > drawings (largest)
  4. Implement LRU eviction for drawings of books not read in 90+ days
  5. For logged-in users, rely on Firestore as the source of truth and use localStorage
     only as a write-through cache (not primary storage)
  The current 'localStorage first' architecture works well for the scale of this project
  but would need redesigning if the annotation feature became heavy."

  Q16: How would you add real-time collaborative reading features
       (e.g., reading clubs where multiple users can annotate the same book together)?
  ────────────────────────────────────────────────────────────────────────────────────
  Testing: System design for new features
  Answer: "The current architecture is purely individual — each user's annotations are
  under their own Firestore path. For collaborative reading:
  
  Architecture changes:
  1. Create a 'reading_rooms' Firestore collection with shared annotation documents
  2. Move shared annotations from users/{uid}/annotations to rooms/{roomId}/annotations
  3. Use Firestore's onSnapshot() real-time listener on the shared annotations document

  4. BookReader.tsx would need to differentiate between own vs. shared annotations in the

  5. Add conflict resolution: Firestore transactions for concurrent annotation edits
  6. Add presence indicators (who's reading which page) via Firestore's Presence API
     or Firebase Realtime Database (better for low-latency presence)
  
  Challenges:
  - PDF page rendering is already client-side; real-time annotation overlay adds
    complexity in coordinate systems
  - Need to handle offline members gracefully
  - Bandwidth: streaming annotation updates for 10+ simultaneous users"

  Q17: The project uses Next.js App Router with React Server Components.
       Explain where RSCs are used and why they matter for performance.
  ────────────────────────────────────────────────────────────────────────
  Testing: Advanced Next.js/React knowledge
  Answer: "React Server Components execute on the server and send pre-rendered HTML,
  reducing the JavaScript bundle sent to the client.
  
  In this project:
  1. app/book/[id]/page.tsx is a Server Component — it generates the book metadata
     (title, description for OG tags) without adding client-side JS
  2. app/layout.tsx is a Server Component that sets up the HTML structure
  3. app/sitemap.ts generates the sitemap on the server
  
  Client Components ('use client') are explicitly marked:
  - BookReader.tsx: needs browser APIs (PDF.js, canvas, localStorage)
  - All Context providers: need React state
  - Navbar.tsx: needs interactive state (search modal, theme dropdown)
  
  Performance benefit: The home page (app/page.tsx) can be partially server-rendered,
  sending initial HTML to the browser faster. The featured books carousel data
  (from static books.json) can be inlined into the HTML without a client fetch.
  
  Key constraint: Server Components cannot use useState, useEffect, browser APIs,
  or Context. Anything interactive must be a Client Component."

  Q18: If this app needed to support 100 languages for translation, how would you
       redesign the translation system?
  ────────────────────────────────────────────────────────────────────────────────────
  Testing: Architecture evolution thinking
  Answer: "Current system: single Gemini call per 2 pages, supports 3 language targets.
  
  At 100 languages, challenges:
  1. COST: Gemini API calls per translation would be expensive at scale
  2. LATENCY: Gemini can be slow for long texts
  3. QUALITY: Gemini quality varies by language pair
  
  Redesign proposal:
  1. Cache layer: Redis/Upstash KV storing translations keyed by (bookId, pageNum, language)
     → 95%+ cache hit rate after first translation of a popular book page
  2. Specialized models: Use Google Translate API (cheaper, faster, 100+ languages)
     for general translation; Gemini only for literary/philosophy texts needing nuance
  3. Pre-translation pipeline: For the 50 most popular books, pre-translate all pages
     of the top 10 languages in a background job, store in Firestore/CDN
  4. Progressive enhancement: Detect user's browser language, pre-translate to that
     language in the background when a book is first opened
  5. Community translations: Allow logged-in users to submit and vote on better
     translations (crowd-sourced quality improvement)
  6. Cost control: Rate limiting per user (already partially in place with daily limits)"

  "Let me go deeper on some interesting technical decisions.

  STORAGE ARCHITECTURE DECISION:
  I consciously chose not to require login for reading because the #1 friction point for
  most reading apps is the signup barrier. By storing everything in localStorage first,
  even guests get a full experience with progress tracking. The keys are namespaced:
  'readershub:progress:v1:{uid}:{bookId}' — for guests, uid is 'guest'. When a user
  logs in, the reconciliation function migrates guest data under their user namespace
  and merges it with any existing cloud data using a best-of-both strategy: higher page
  number wins, sets are unioned, etc.

  READER COMPONENT COMPLEXITY:
  BookReader.tsx is the core of the application at 3,538 lines. It manages PDF rendering
  via a vendored PDF.js worker (served from /vendor/pdfjs/ to avoid CORS issues), handles
  double-page and single-page layouts, text selection for highlights, an overlaid freehand
  drawing canvas, session timers, keyboard shortcuts, and touch gestures for mobile.
  I kept it as one large component rather than splitting it too aggressively because the
  state interactions between PDF page position, annotations, translations, and the timer
  are tightly coupled.

  AI GROUNDING STRATEGY:
  The key challenge with Gemini for the assistant was preventing hallucination — Gemini
  is trained on general internet data and knows about thousands of books. I need it to
  only recommend books actually in my library. The solution is to inject the entire
  catalog (grouped by category, ~386 entries) into the system instruction and explicitly
  forbid references to books not in the list. For very common queries like 'What books
  do you have?' I added deterministic regex pattern matching that bypasses Gemini entirely
  for zero latency.

  PAYMENT ARCHITECTURE:
  Razorpay requires that the amount is always determined server-side — you cannot trust
  the client to send the correct amount. In create-order/route.ts, I read the plan amount
  from monetization-config.ts on the server, not from the request body. The planId is
  validated, but the amount is always taken from the server's source of truth. Payment
  verification uses HMAC SHA256 with crypto.timingSafeEqual() which is the industry
  standard for preventing timing side-channel attacks.

  CONTENT POLICY:
  The project includes a content-rights-audit.json and a content policy mode
  (audit/hide_review_required/legal_only) which reflects that some books in the catalog
  may have copyright considerations. The monetization-config.ts explicitly notes that
  ads require 'legal_only' mode — ads cannot show on pages with potentially rights-restricted
  content. This shows thinking about responsible publishing at scale."

  INTERVIEWER: Tell me about Reader's HUB.
  YOU: [30-second explanation from §22]

  INTERVIEWER: Why did you store reading data in localStorage instead of a database?
  YOU: "The main reason was zero-barrier access. If I required a database write on every
  page turn, unauthenticated users couldn't track progress. localStorage gives instant,
  offline-capable persistence with zero network dependency. For logged-in users, I do
  sync to Firestore asynchronously — but localStorage is always the source of truth for
  the reading experience."

  INTERVIEWER: What happens if localStorage is cleared?
  YOU: "For guests, the data is lost — that's an accepted tradeoff of the no-login model.
  For logged-in users, the data is backed up in Firestore and gets restored on next login
  via the reconcileAndSyncAllUserData() function in lib/firestore-sync.ts. I could reduce
  this risk by periodically syncing to Firestore more aggressively, but I debounce writes
  to avoid database costs."

  INTERVIEWER: How does the request reach the Gemini AI?
  YOU: "The user types in LibraryAssistant.tsx → it calls fetch('/api/chat', { method: POST,
  body: { message } }). This hits app/api/chat/route.ts, a Next.js Route Handler running
  on Vercel serverless. It first calls tryDeterministicQuery() — if the message matches
  common patterns, it returns immediately without touching Gemini. Otherwise, it builds
  a system prompt containing all 386 books grouped by category, creates a GoogleGenAI
  instance with the GEMINI_API_KEY from env, and calls ai.models.generateContent() with
  temperature 0.2 (low creativity for factual accuracy). The response comes as JSON,
  parsed, and the book IDs are resolved to full Book objects before returning to the client."

  INTERVIEWER: Why did you use Firebase specifically for authentication?
  YOU: "Firebase Auth provides Google OAuth out of the box with minimal code — I get the
  popup flow, token management, session persistence, and secure token verification via the
  Admin SDK for free. The alternative would have been building a custom OAuth flow with
  NextAuth.js or Auth.js, which adds a server session database requirement. Firebase also
  has a generous free tier. The tradeoff is vendor lock-in to Google's ecosystem, but
  given I'm already using Firestore and Google's AI, this was a coherent choice."

  INTERVIEWER: How would you scale this if it got 100,000 daily active users?
  YOU: "Three main pressure points. First, the Gemini API — I'd add server-side rate limiting
  per user, a Redis caching layer for repeated queries (same books asked many times), and
  potentially a dedicated Gemini service account with higher quotas. Second, Firestore —
  my debounced writes are already good, but I'd add the ability to batch writes using
  Firestore's writeBatch for the sync operation. Third, PDFs — currently on Vercel's CDN
  which handles scale well, but I'd migrate to Cloudflare R2 or AWS S3 with CloudFront for
  cost optimization at high bandwidth. The books.json static catalog scales perfectly —
  it's just a JSON file on CDN. LocalStorage analytics scale infinitely since they're
  client-side. So the main costs to control are AI API and Firestore."

  INTERVIEWER: What happens under high traffic to the translation endpoint?
  YOU: "Each translation request is independent (no shared state) so it scales horizontally

  server-side quota tracking — the 10 spreads/day limit is enforced client-side via
  localStorage, which can be bypassed. Under traffic, I'd add:
  1. Redis-based server-side rate limiting per user/IP
  2. A translation cache: if the same page of the same book has been translated before,
     return the cached result instead of calling Gemini
  3. Request queueing to prevent thundering herd during peak hours
  4. Cost monitoring alerts on the Gemini API dashboard"

  INTERVIEWER: Where is the authentication middleware in this project?
  YOU: "There's no middleware.ts file — Next.js middleware at the request level isn't used.

  AuthGuard.tsx and AdminGuard.tsx check the auth state from AuthContext and redirect
  or show a login prompt. This is a reasonable approach for this scale — global middleware
  would add overhead to every request including public ones."

  4. Error monitoring: Add Sentry for production error tracking — currently there's no

  5. Content security: The books.json is publicly editable via deployment; a more robust

  6. CI/CD: Add GitHub Actions with automated build checks, ESLint, and basic smoke tests
