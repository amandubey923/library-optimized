# Reader's HUB — Reusable PDF Ingestion & Catalog Integration

New PDF files have been added to the project's PDF asset folder.

Treat these files as a **new batch of resources to be safely integrated into the existing Reader's HUB catalog**.

This prompt may be reused repeatedly in the future whenever new PDFs are added.

---

# ABSOLUTE RULE

## EXTEND — DO NOT BREAK EXISTING PROJECT

The existing Reader's HUB is stable and production-quality.

DO NOT:

* rewrite the project
* redesign the UI
* replace the reader
* change PDF.js
* change existing reader behavior
* change existing book IDs
* change existing localStorage identities
* change existing progress data
* change annotations
* change bookmarks
* change streak/Diya
* change Translation
* change Focus Mode
* change PWA/offline architecture
* change existing categories unnecessarily
* modify existing PDFs unless explicitly required
* delete existing books
* delete existing catalog entries
* blindly refactor unrelated code

This is an **additive catalog ingestion task**.

The existing catalog must remain intact.

---

# PHASE 1 — DISCOVER NEW FILES

First inspect the actual filesystem.

Find all newly added PDF files.

Do NOT assume the filenames listed in this prompt are the complete inventory.

Build an inventory from the project filesystem.

For every new PDF identify:

* current filename
* file size
* page count
* title
* author/source
* subject
* likely category
* resource type
* whether handwritten
* whether a book
* whether notes
* whether cheat sheet
* whether interview preparation
* whether technical or literary
* whether duplicate/similar to an existing resource

DO NOT modify anything during this phase.

---

# PHASE 2 — DO NOT TRUST FILENAMES

Many files may have poor filenames.

Examples:

* abbreviations
* random numbers
* personal download names
* `(1)`
* `(2)`
* `final`
* `new`
* `notes`
* `download`
* `scan`
* emoji
* brackets
* inconsistent casing

Do NOT infer the actual title only from filename.

Use the PDF itself when necessary:

* title page
* first page
* headings
* author/source
* metadata
* document content
* visible subject

Correct identification matters more than naming.

If the identity is ambiguous:

DO NOT guess.

Mark:

`UNKNOWN / NEEDS REVIEW`

---

# PHASE 3 — DETECT WHETHER RESOURCE ALREADY EXISTS

Before adding a new resource, compare against the existing catalog.

Check for:

* exact duplicate
* same title
* same book with different edition
* same notes with slightly different filename
* same content under another filename

Use multiple signals:

* filename
* title
* author/source
* page count
* content similarity where practical

### If exact duplicate:

Do NOT add a duplicate catalog entry.

Report it.

### If same subject but meaningfully different resource:

Keep both.

Example:

`SQLInterviewQuestions.pdf`

and

`SQLAdvancedInterviewQuestions.pdf`

can both be valid.

---

# PHASE 4 — CHOOSE A MEANINGFUL TITLE

Create a clean human-readable title.

Priority:

1. Actual title from PDF
2. Verified title from document content
3. Verified author/source if available
4. Only then use filename as supporting evidence

Do not invent titles.

---

# PHASE 5 — CANONICAL PDF FILENAME

Rename new PDF files using the project's established naming convention.

## Rules

Use:

**CamelCase / PascalCase**

No unnecessary spaces.

No emojis.

No brackets.

No random download suffixes.

No invalid Windows characters.

No personal abbreviations.

Examples:

`computer networks final v2.pdf`

→

`ComputerNetworksCompleteNotes.pdf`

`sql 100 imp interview qs.pdf`

→

`SQL100InterviewQuestions.pdf`

`python handwritten.pdf`

→

`PythonCompleteHandwrittenNotes.pdf`

`system design notes (1).pdf`

→

`SystemDesignCompleteArchitectureNotes.pdf`

---

# PHASE 6 — FULL TITLE WHEN PRACTICAL

Prefer the full meaningful title.

But if it becomes excessively long:

* shorten intelligently
* preserve recognition
* preserve important author/source information only when needed

Do NOT create unreadably long filenames.

---

Classify each new PDF.

Possible values:

* `Book`
* `Notes`
* `HandwrittenNotes`
* `CheatSheet`
* `InterviewPrep`
* `Reference`

Use the existing project's data model if it already supports these.

Do not create duplicate type systems.

* DSA & Problem Solving

* Web & Backend Development
* DBMS & SQL
* OOP & Software Design
* System Design & DevOps

Examples:

* Romance

* Fantasy & Adventure

Do NOT create a new top-level category unless the current taxonomy genuinely cannot represent the resource.

# PHASE 9 — IMPORTANT TECHNICAL KNOWLEDGE RULE

All technical PDFs should appear under:

Do NOT create new top-level cards such as:

* title

* category

* resource type

* description

# PHASE 11 — UNIQUE STABLE ID

Generate a unique stable slug-like ID.

Example:

`system-design-complete-architecture-notes`

Do NOT use:

* random runtime IDs
* filename hashes
* temporary timestamps

Once created, this ID must remain stable even if the PDF filename is later changed.

# PHASE 14 — HANDLE SAME SUBJECT MULTIPLE PDFs

Do NOT merge different resources merely because they cover the same subject.

→ SQL

* SQL Top 100 Interview Questions
* SQL Interview Quick Cheatsheet

# PHASE 15 — HANDWRITTEN / SCANNED PDF HANDLING

If the PDF is:

* handwritten
* image-only
* scanned

mark its resource type appropriately.

Do not pretend it has selectable text if it does not.

Reader should still work.

Search/translation should gracefully handle missing text layers.

Do NOT automatically run OCR across the entire library.

If both exist, preserve their existing synchronization strategy and update them consistently.

